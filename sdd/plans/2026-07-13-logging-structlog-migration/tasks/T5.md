Todos: `import logging` → `import structlog`, `logger = logging.getLogger(__name__)` →
`logger = structlog.get_logger(__name__)` (o `_logger = ...` en `core/database.py`,
respetando el nombre de variable existente). Verificado con `grep -n "logging\."`
por archivo antes de tocar el import.

## Excepción — archivos que conservaron `import logging`

- `backend/auth/email.py`: usa `logging.ERROR` / `logging.WARNING` como argumento
  de `logger.log(level, ...)` en `dispatch_or_log`. Conserva `import logging` +
  agrega `import structlog`.
- `backend/run_migrations.py`: usa `logging.basicConfig(level=logging.INFO)` en el
  bloque `if __name__ == "__main__":`. Conserva `import logging` + agrega
  `import structlog`.
- `backend/main.py`: **NO** conservó `import logging`. Se revisó con grep antes del
  swap — el único uso de `logging.` en el archivo era `logging.getLogger(__name__)`
  (línea 45), sin ningún otro uso de la constante/API de `logging`. Aplica el swap
  normal (`import logging` → `import structlog`), tal como anticipaba el prompt.
- `backend/worker.py`: no tenía `import logging` a nivel de módulo, sino un import
  local dentro de un `except` en `resume_orphans` (`import logging;
  logging.getLogger(__name__).exception(...)`). Se eliminó ese import local y se
  promovió `logger = structlog.get_logger(__name__)` a nivel de módulo (mismo
  patrón que el resto del batch), en vez de dejar un logger ad-hoc dentro del except.

## Archivos sin llamadas `logger.*` dinámicas

`auth/totp_router.py`, `auth/session_router.py`, `auth/router.py` y
`rag/store.py` declaran `logger`/tienen `logger = logging.getLogger(__name__)`
pero no lo usan en ningún punto del archivo — se migró igual el import/logger por
consistencia con el resto del batch, sin cambios de mensaje (no hay ninguno).

## Decisiones de naming kv

- `error=str(exc)` en vez de interpolar la excepción directo en el mensaje
  (patrón consistente con batches anteriores).
- `to_email` / `log_label` en `email.py`: se mantienen los mismos datos que ya se
  logueaban antes (dirección de correo, no un secreto); el enlace con el token no
  se loguea nunca, respetando el comentario existente en `dispatch_or_log`.
- `filename` en vez de `file` (más explícito, evita colisión conceptual con
  file-handles en el código circundante).
- Ningún campo usado colisiona con los reservados de structlog (`event`, `level`,
  `logger`, `timestamp`, `exc_info`, `stack_info`).
