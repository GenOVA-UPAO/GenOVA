# T6 — Wiring Logfire → structlog (Batch F, final)

Objetivo: que las líneas de log kv-pair emitidas por `structlog.get_logger` (los
83 archivos de T1-T5) lleguen a Logfire como campos SQL-queryables, no solo los
spans automáticos de FastAPI/SQLAlchemy/OpenAI que ya instrumentaba
`init_logfire`.

## Problema de orden resuelto

`logfire.StructlogProcessor()` necesita: (a) estar en la lista `shared` de
processors ANTES del renderer final, y (b) que `logfire.configure(...)` ya
haya corrido. Pero `configure_logging()` corría en el import de `main.py`
(línea ~44) y `logfire.configure(...)` vivía dentro de `init_logfire()`, que
corre mucho después (línea ~167, tras crear `app`). Solución: mover
`logfire.configure(...)` DENTRO de `configure_logging()`, antes de construir
`shared` y antes de `structlog.configure(...)`.

## Archivos tocados

### `backend/core/logging_setup.py` (líneas ~19-61 tras el cambio)

- Firma de `configure_logging`: agregado parámetro `logfire_token: str = ""`
  (enfoque explícito, no import de `settings` — evita acoplar el módulo a
  `core.config`; confirmado sin import circular, `core/config.py` no importa
  `core.logging_setup`).
- Nuevo bloque `if logfire_token:` justo después de construir `shared` (antes
  de `structlog.configure(...)`): `import logfire` local (para no forzar el
  import del paquete cuando no hay token — verificado con
  `sys.modules` que `logfire` NO se importa si `logfire_token=""`),
  `logfire.configure(token=logfire_token, service_name="genova-backend",
  environment=env, console=False)`, luego `shared.append(logfire.StructlogProcessor())`.
- Orden dentro de `shared`: `logfire.StructlogProcessor()` se agrega DESPUÉS
  de `redact_event_dict` (R8 — Logfire solo recibe datos ya redactados, nunca
  secretos/PII crudos) y ANTES de
  `structlog.stdlib.ProcessorFormatter.wrap_for_formatter` (ese último sigue
  fuera de `shared`, agregado solo en el `processors=[*shared, ...]` de
  `structlog.configure`, como ya estaba).
- `try/except Exception` alrededor de todo el bloque de `logfire.configure`:
  en el `except` se usa `logging.getLogger(__name__).exception(...)` (logger
  stdlib local, no `structlog`, porque en ese punto el pipeline structlog aún
  no está armado) — replica el nivel de robustez de `init_logfire` (nunca
  rompe el arranque del backend).
- El resto de la función (`renderer`, `formatter`, `handler`, loop de
  `uvicorn`/`uvicorn.error`/`uvicorn.access`) queda igual, sin cambios de
  línea salvo el desplazamiento por el bloque nuevo.

### `backend/core/observability.py` (archivo completo re-escrito, 40 líneas)

- `import logging` → `import structlog`; `logger = logging.getLogger(__name__)`
  → `logger = structlog.get_logger(__name__)` (era el único archivo de la
  migración T1-T5 que quedaba pendiente, mencionado explícitamente en el
  prompt de T6).
- `init_logfire(app, engine)`: se quitó la llamada a `logfire.configure(...)`
  (ahora vive en `configure_logging`). Se dejó solo
  `logfire.instrument_fastapi(app, capture_headers=False)`,
  `logfire.instrument_sqlalchemy(engine=engine)`, `logfire.instrument_openai()`,
  con el mismo guard `if not settings.logfire_token: return` y el mismo
  `try/except Exception` + `logger.exception(...)`.
- Docstring de `init_logfire` actualizado para explicar que `configure` ya
  corrió antes. Log final cambiado de "Logfire inicializado" a "Logfire
  instrumentado" (más preciso: ya no configura, solo instrumenta).
- `init_langsmith()` sin cambios (no tocaba `logging.getLogger`).

### `backend/main.py` (línea 44, único call-site)

- `configure_logging(log_level=settings.log_level, env=settings.env)` →
  `configure_logging(log_level=settings.log_level, env=settings.env,
  logfire_token=settings.logfire_token)`.
- Orden de llamadas sin cambios: `configure_logging(...)` sigue siendo la
  primera línea ejecutable tras los imports (línea 44-46); `init_logfire(app,
  engine)` sigue llamándose tras crear `app` (línea ~167-169).

## Grep final `logging.getLogger` en `backend/` — NO da 0 resultados; detalle

Quedan 5 matches, todos legítimos (no son loggers de aplicación pendientes de
migrar, son usos directos de la API stdlib `logging` por diseño):

- `core/logging_setup.py:55` — `logging.getLogger(__name__).exception(...)`
  dentro del `except` de la configuración de Logfire. **Agregado por este
  mismo T6**, instruido explícitamente por el prompt (en ese punto el
  pipeline structlog aún no existe, no se puede usar `structlog.get_logger`
  todavía).
- `core/logging_setup.py:86` — `root = logging.getLogger()` (logger raíz
  stdlib, para instalar el `handler`). Preexistente, es la función que
  configura stdlib logging en sí misma, no un logger de módulo.
- `core/logging_setup.py:92` — `ul = logging.getLogger(name)` dentro del loop
  que limpia handlers de `uvicorn`/`uvicorn.error`/`uvicorn.access`.
  Preexistente, mismo motivo.
- `tests/test_logging_setup.py:22` y `:28` — `logging.getLogger("test.structlog")`
  usado deliberadamente para emitir vía un logger stdlib "foreign" y verificar
  que el `handler`/`ProcessorFormatter` de `configure_logging` lo captura y
  formatea. Preexistente, es la prueba de integración con stdlib, no un logger
  de aplicación.

Ninguno de los 5 es un `logger = logging.getLogger(__name__)` de módulo de
aplicación sin migrar — el único que existía (`core/observability.py`) se
migró en este mismo T6. No es un bug de un batch anterior.
